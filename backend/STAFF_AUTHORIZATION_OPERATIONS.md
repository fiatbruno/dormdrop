# Staff role changes and WebSockets

`PATCH /api/v1/admin/team/{userId}/role` accepts `{"role":"STUDENT"}`, `MODERATOR`, or `ADMIN`. Only administrators may call it, and targets must have verified `@augustana.edu` email addresses. A role change and its immutable application audit entry are written together. The shared guard document serializes role changes so simultaneous demotions cannot remove the last administrator. A conflict returns 409 and may be retried. A request that does not change the role creates no audit entry.

Role management requires MongoDB transactions with snapshot reads and majority writes. Configure a replica set or sharded cluster; a standalone MongoDB server cannot perform these writes. The repository describes a local MVP, not a deployed topology, so deployment support must be verified before enabling role management. The database account must be able to write the `role_change_guard` and `role_changes` collections and should prevent application-independent modification of audit entries.

Every committed change increments the user's durable role version in the same transaction. The local instance closes the user's sockets after commit. Each instance also checks authenticated socket versions against MongoDB every second and closes stale sessions; a missing account or database read failure closes affected sockets. This polling is eventually consistent: a remote socket may remain connected until the next successful check, plus database and scheduler latency. Thus this mechanism does not provide strictly instantaneous revocation. Reconnecting reloads the role, and existing HTTP tokens resolve the database role on each request. A database outage causes sockets to close; users must reconnect once the database recovers. The check assumes reads go to the primary, so do not configure stale secondary reads. No invalidation is issued for a rolled-back change.

A transaction commit can have an unknown outcome if the database connection fails during commit. In that case the API may return 409 even if the transaction committed. Before retrying, inspect the current role and audit history; the durable role version still causes socket invalidation if the commit succeeded.
